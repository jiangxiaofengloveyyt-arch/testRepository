# 公共运行细则（从实战手册抽取）

本文件把多轮自动开发实战手册中可跨模块复用的操作规则单独列出。它是公共规则，不包含 NCM、NSH、合同业务或仓储业务的专属路径和字段；模块专属配方仍由当前仓库的 `references/domain.md` 负责路由。合同历史手册保留完整原文，便于审计和追溯。

## 1. 真实红灯与有效绿灯

1. 红灯必须由目标行为的断言失败产生：先锁定真实入口、真实 DTO/字段、真实持久化或外部边界，再执行最小可失败测试。
2. 编译失败、依赖下载失败、网络超时、测试夹具缺字段、路径写错或启动参数错误，只能记录为环境/夹具阻断，不能冒充业务红灯。
3. 绿灯必须重跑同一条红灯命令，并补充必要的回归命令；只看到“编译通过”不能证明目标行为修复。
4. 夹具要覆盖真实序列化、空值、边界值和权限/租户上下文。优先复用生产代码使用的 mapper、service、controller 或导入导出入口，不要在测试里另造一套绕过缺陷的对象。

## 2. JIRA 唤醒与去重

定时任务可用“项目/过滤器范围 + 状态候选 + 变更水位线 + 任务锁”组成幂等取单机制：

- 每轮先读取上次成功水位线，再扫描目标状态和指定时间窗内的 changelog/comment 事件；没有新事件时静默退出。
- 以事件时间、事件 ID（若可用）或组合指纹做去重，不以“最后修改人”推断是否为人工唤醒。
- AI 自己写的评论、状态变化和分支/PR 回写不得自激唤醒；应记录自己的事件指纹并在下轮排除。
- 只有明确的人工事件、显式重跑命令或状态重新进入候选集时才允许重处理；重处理前仍要重新校验锁、风险和工作树。
- 水位线更新必须在本轮证据落盘后进行；中途失败不得前移水位线，否则会吞掉工单。

项目编号、过滤器 ID、状态名、标签和字段名必须来自当前模块的 `config/module.toml` 或 JIRA 实际响应，不能从本文件复制。

## 3. 环境、基线和阻断诊断

- 先用配置解析器得到实际路径、分支和工具，再执行写操作；不要猜测工作区、模块或启动参数。
- 记录基线命令及其结果。若基线本身失败，保留失败输出，判断它是既有失败、环境阻断还是本工单回归，并在报告中分栏说明。
- 看到一次命令失败时，先区分代码错误、依赖/网络错误、权限错误、夹具错误和工具缺失；能通过更窄的受控命令验证就不要直接扩大改动范围。
- 不能因为环境问题擅自修改依赖、关闭质量门禁、跳过测试或改写共享配置；需要人工授权时转黄灯并停止高风险动作。

## 4. 交付证据

每个工单至少落盘以下证据，并让证据能回指到实际文件、命令和时间：

- JIRA Key、风险颜色、取单/锁单/唤醒事件与水位线；
- 变更文件清单、分支、commit、push、PR 目标基线和 JIRA 回写结果；
- 红灯命令与失败断言、绿灯命令与结果、回归/构建结果及基线失败对照；
- Code Review 结论、人工验收步骤、未执行项、阻断原因和剩余风险。

证据中不得写入 token、密码、Cookie、完整连接串或未经脱敏的客户数据。日志需要保留最小可复现片段和脱敏说明，而不是整段复制凭据环境。

## 5. Code Review 与安全边界

- Code Review 既检查功能正确性，也检查权限/租户隔离、SQL 注入与越权、异常处理、日志脱敏、幂等性、事务边界、性能和测试覆盖。
- 发现高置信度缺陷时回到 plan/tasks 修复并重新跑红绿与评审；不能用“后续优化”掩盖阻断项。
- AI 的标准终点是候选 commit、push、PR 和 JIRA 证据。AI 不合并 PR、不向基线直接推送、不部署、不触发发布、不操作生产/共享环境，也不删除任务分支。

## 6. 返工和人工接管

红灯、黄灯、绿灯的状态变化都要写入证据。若遇到缺少授权、跨仓协议不明、基线与工单冲突、数据库/外部系统写操作或无法脱敏的真实数据，立即转人工；人工补充信息后从预检、锁单和基线重新开始，不能沿用未验证的中间结论。
