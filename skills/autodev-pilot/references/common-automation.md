# 通用自动开发运行手册

本文件是所有仓库 `autodev-pilot` 的公共功能基线。领域覆盖文件只能加严风险、补充代码地图和验证命令；不得降低本文件的交付门禁。配置、项目规则和本轮人工指令冲突时，以更严格者为准。

## 0. 预检与空轮早退

1. 在当前仓库根目录运行 `scripts/config_loader.py validate` 和 `resolve`；只使用其输出的仓库、模板、规格、worktree、证据和工具路径。预检失败时不取单、不改代码。
2. 从配置的 JIRA 项目、筛选器、标签和可处理状态查询候选工单。没有候选时只记录查询条件、原始计数和本轮时间，然后结束；不得创建 worktree、运行构建或修改 JIRA。
3. 取单前检查本地状态台账、同名 `ai/<JIRA_KEY>` 分支、已有 `[AI-AUTO-DEV] RUNNING` / `DONE` 评论和未关闭 PR。已在运行或已交付的工单跳过，避免并发重复执行。

JIRA 筛选器、状态名、字段和 API 能力必须在目标项目实测或配置中给出；禁止照搬其他仓库的 filter id、transition id、客户字段或远端地址。

## 1. 领取、澄清与风险路由

1. 完整读取工单标题、描述、评论、附件、验收标准、目标模块与环境，并阅读目标目录最近的 `AGENTS.md`。
2. 缺少当前行为、目标行为、验收标准或目标模块时，写 `[AI-AUTO-DEV] YELLOW` 评论（若本轮有 JIRA 回写权限），列明缺失字段后停止；不建分支、不猜测业务规则。
3. 信息完整后，以原模板建立 `intent.md`、`spec.md`、`plan.md`、`tasks.md`、`code-review.md` 和人工验收清单，并记录初始风险路由。
4. 在写代码前领取工单：写 `[AI-AUTO-DEV] RUNNING`（含 run_id、时间和 agent）并按目标项目可用流转进入“执行中”。写评论或流转失败时，停止该工单。

| 路由 | 判据与 AI 动作 |
| --- | --- |
| 绿 | 有明确目标、最小改动边界、可构造有效红灯或目标行为测试、可做受控真实链路验证，且不触及红灯项；可完整实施。 |
| 黄 | 范围、口径、环境、失败归属、前端模块来源、依赖/兼容性或验证方案仍不确定；仅调查、方案、测试设计和待确认项。人工确认后重新判定。 |
| 红 | 生产/共享环境写入、凭据、权限/认证、租户隔离、不可逆数据、数据库结构/迁移、公开 API/跨服务契约、部署/基础设施，或只能在生产验证；仅只读分析与转人工。 |

任一时刻发现风险升级、修改面超出计划、无法形成有效红灯或真实链路未覆盖，立即转黄或红，不得以“需求简单”降级。

## 2. 隔离开发与 TDD

1. 共享主工作区必须干净；若有来源不明改动，停止并报告，绝不 `reset`、`checkout`、`clean` 或覆盖他人工作。
2. 从配置的基线分支获取最新远端提交，在 `${paths.backend_worktree}`（前端任务使用 `${paths.frontend_worktree}`）创建或安全复用 `ai/<JIRA_KEY>` worktree。worktree 损坏时先把本单差异和未跟踪测试备份到证据目录，再 prune/recreate，并用 `git diff --stat` 核验恢复；不得丢弃改动。
3. 先写一个能稳定失败、且失败落在目标断言的最小测试；实现只满足该场景，再补边界、异常和回归测试。新增功能没有旧行为时，未实现前的目标行为测试失败也可作为红灯。
4. 不能安全运行自动测试时，必须在 `plan.md` 写明原因、可复现替代验证和剩余风险；不把编译错误、依赖下载失败、夹具错误或主观分析当作红灯。
5. 遇到全量测试失败，先在无本单改动的相同基线复现。仅当基线同样失败且证据可复核时，标为“基线既有失败”；仍需在交付中单列，不能宣称全绿。

## 3. 验证与 Code Review 门禁

按仓库实际能力执行：目标测试 → 受影响模块构建/测试 → 可行的更高层回归 → 至少一种受控真实链路（真实入口、真实文件、dry-run、容器或等价验证）。每项记录完整命令、退出码、关键结果和未执行原因。

实现完成后，按 `templates/code-review.md` 进行独立审查。至少检查：

- 是否只满足已冻结的规格，是否引入范围外重构；
- 空值、边界、异常、事务/并发/幂等和回滚；
- 数据隔离、权限、软删除、审计字段、外部契约与兼容性；
- SQL/前端/API 是否遵循目标仓库已有模式；
- 测试是否真的覆盖修复点，是否泄漏凭据、客户数据或环境地址。

发现阻断项、测试失败或验收缺口，不能进入交付门禁。

## 4. 交付门禁：commit、push、PR、JIRA

本试点公共默认终点是：**绿色门禁通过后，本地候选 commit + push `ai/<JIRA_KEY>` + 创建或更新 base 为配置基线的 PR + JIRA 交付评论**。这是合同试点已固化的自动化链路；目标仓库若没有可用远端、PR 或 JIRA 回写权限，必须在配置/任务中显式关闭相应步骤并报告，不得伪造成功。

1. 先检查 `git status`、`git diff`、敏感信息和任务范围；只以精确路径暂存，禁止 `git add -A`。
2. 提交信息使用 `<JIRA_KEY>: <简短说明>`，保留测试/证据结论。
3. 仅 push `ai/<JIRA_KEY>`，幂等地创建或更新 PR；PR base 必须是配置基线，禁止向 base 直接推送、force push 或合并。
4. 在 JIRA 写 `[AI-AUTO-DEV] PR-READY` / `DONE`：分支、commit、PR、红绿证据、验证结果、Code Review 结论、人工验收步骤和剩余风险。状态流转只能使用当前工单可用的 transition；不编造日期、工时、审批或其他人工承诺字段。
5. AI 永不合并 PR、删除本地/远端任务分支、部署、触发发布或向生产/共享环境写数据。Code Review 签署和最终验收属于人工。

## 5. 人工反馈与再次入队

人工补充描述/评论、显式 `RERUN`、测试退回或进入“重处理”后，先读取增量事实和上轮证据，再重新判路由；不要重复贴整份旧结论。AI 自己写的评论/状态变更不能触发自己再次领取。重复三次仍无法转绿时，置为 HOLD 并明确需要的人工决策；显式重跑可解除 HOLD。

## 6. 证据与收尾

每单在 `${paths.specs}/<JIRA_KEY>/` 和 `${paths.evidence}/<JIRA_KEY>/` 留存：工单快照与风险结论、五件套、最终 diff 摘要、红绿/构建日志、基线失败复核、Code Review 结论、PR/JIRA 回写结果、人工验收清单和未验证风险。证据不得包含密码、Token、完整敏感配置或客户数据。

任务完成后可清理构建产物；worktree 仅在分支、证据和 PR 均已可复现时才清理。分支和 PR 保留给人工评审与合并。
