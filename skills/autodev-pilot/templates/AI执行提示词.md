# 简单开发任务 AI 执行提示词

以下提示词默认用于已经完成 `intent.md`、`spec.md`、`plan.md`、`tasks.md` 和 `code-review.md` 模板准备的绿色任务。使用前替换所有 `{{...}}`。如果任务为黄色，只使用“只调查并建立红灯或目标测试”；红色任务不得使用自动实现提示词。

## 端到端执行提示词

```text
你正在处理简单开发任务试点工单 {{工单号}}。

请先完整读取并遵守：
1. 项目根目录及目标目录中的 AGENTS.md / agents.md；
2. {{工单目录}}/intent.md；
3. {{工单目录}}/spec.md；
4. {{工单目录}}/plan.md；
5. {{工单目录}}/tasks.md；
6. {{工单目录}}/code-review.md（作为本轮评审记录模板）；
7. 文档中列出的项目资料和验证命令。

目标：把已确认的任务目标转化为有效红灯或目标行为测试，用与测试一一对应的最小修改实现，再以同一断言、分层回归和真实链路证明转绿。

执行边界：
- 先检查工作区状态和现有 diff；用户已有修改不得覆盖、回退或格式化。
- 先复核入口风险灯色。绿色才可端到端实施；黄色只调查、建红灯或目标测试和给方案；红色只读分析并转人工。
- 调查、修改、提交是不同授权。本提示词只授权在 plan.md 明列范围内修改测试和实现代码。
- 不提交、不推送、不切换分支、不合并、不部署、不执行生产写操作。
- 不安装依赖、不访问未批准外部系统、不使用或输出密钥、Token、真实个人信息或客户数据。
- 不做无红灯或目标测试证据的顺手修改、重构、全仓格式化或范围扩张。

阶段一：只建立红灯或目标行为测试，先不要修改实现代码。
1. 根据 intent/spec 复述任务目标、当前基线、期望结果和核心断言；发现歧义立即停下。
2. 沿真实入口定位最小实现路径、直接调用方和现有测试。
3. 构造最小但忠于现场的夹具或目标场景，说明它保留了哪些触发关系。
4. 只修改测试，运行并确认实现前稳定失败在预先约定的目标断言。
5. 区分：功能失败、测试自身错误、环境故障、既有不稳定、无关失败。
6. 如果不能形成有效红灯或目标行为测试，不得把任务列为已确认，不得改实现代码；报告原因并停下。
7. 输出红灯/目标测试证据、原因事实与推断、影响范围、最小实现方案，并更新 tasks.md 的 G1 证据。

阶段二：仅当有效红灯或目标行为测试成立、入口仍为绿色且文档已有实施授权时继续。
1. 只修改红灯或目标测试证明相关的实现路径，每处修改映射到测试编号和规格场景。
2. 不弱化或改写原断言来制造绿灯，不删除/跳过测试，不扩大容差掩盖问题。
3. 运行同一红灯或目标行为测试，确认同一断言因实现转绿。
4. 补齐并运行适用的正向、负向和边界测试。
5. 依次运行 plan.md 中的定向测试、模块测试、全量测试、静态检查或构建。
6. 对每个失败单独分类；稳定失败不能用“可忽略”带过。
7. 用 plan.md 指定的真实文件、实际入口、本地容器或 dry-run 验证实际接线，防止单元测试绿但实际路径仍走旧逻辑。
8. 检查最终 diff、工作区、生成产物和修改范围，清理本次临时对象。
9. 更新 tasks.md 的证据字段。不要替人工勾选人工确认或验收项。

阶段二.5：Code Review 门禁（在分层测试前）
1. 对照 `intent.md`、`spec.md`、`plan.md` 和最终 Diff，完成 AI 自审，检查范围越界、规格一致性、异常处理、安全、性能、并发、兼容性、真实接线和敏感信息。
2. 填写 `code-review.md`，逐项记录实现映射、测试支撑、发现的问题、阻断项和证据位置。
3. 等待人工评审人独立完成 Code Review 并在 `code-review.md` 记录结论；评审未通过不得进入分层测试或候选提交。
4. 评审退回时只修复已记录阻断项并重新评审；转黄/转红时立即停止自动执行并按路由报告。

停止条件：
- 需求或规格存在歧义；
- 红灯或目标行为测试无效或不可重复；
- 需要修改 plan.md 未列文件或改变规格；
- 涉及外部契约、数据结构、支付/金额、权限、安全、隐私、幂等、事务、并发、异步、恢复点、部署或生产操作；
- 回归出现稳定新失败且无法证明与本次无关；
- 真实入口未命中新逻辑；
- 工作区存在来源不明或与本次重叠修改。

命中停止条件时立即停止修改，用“转黄”或“转红”报告：触发条件、已完成工作、现有证据、工作区状态、需要人工决定的问题。不要自行扩大授权。

最终汇报必须按以下结构，不要只说“已完成”或“测试通过”：
1. 入口路由：灯色、理由、是否发生升级；
2. 红灯/目标测试证据：测试名、完整命令、实现前失败断言与摘要；
3. 原因或实现依据：已证实事实与仍属推断的内容；
4. 修改映射：文件、关键修改、对应红灯/目标测试/规格；
5. Code Review 证据：AI 自审、人工评审人、结论、阻断项、复核记录和 `code-review.md` 位置；
6. 绿灯证据：同一测试、定向、模块、全量、静态/构建的命令和结果；
7. 真实链路：步骤、脱敏输入、实际结果；
8. 异常分类：本次回归、既有不稳定、环境问题；
9. 范围证据：最终 diff、工作区、产物、清理结果；
10. 遗留风险和需要人工验收的项目。
```

## 只调查并建立红灯或目标测试

```text
工单：{{工单号}}
现象：{{最小输入、当前结果或截图位置}}
期望：{{可断言的期望结果}}

请先读取 {{工单目录}} 下的 intent.md、spec.md、plan.md、tasks.md、code-review.md 以及项目 AGENTS.md / agents.md。

本轮只调查并建立红灯或目标行为测试，不修改实现代码：
1. 检查工作区和现有 diff，保护用户已有修改；
2. 用最小但忠于现场的夹具复现；
3. 先运行测试，确认失败发生在预期业务断言；
4. 区分功能失败、测试自身错误、环境故障、既有不稳定和无关失败；
5. 给出原因事实与推断、影响范围和最小实现方案；
6. 填写 tasks.md 的 G1 证据，不替人工确认。

如果无法构造有效红灯或目标行为测试，请不要把任务列为已确认，也不要修改实现代码。提交、推送、部署和生产操作均未授权。
```

## 红灯或目标测试确认后实施修改

```text
沿用工单 {{工单号}} 已由 {{确认人}} 于 {{时间}} 确认的红灯或目标测试 {{红灯编号}} 实施最小修改。

要求：
- 完整遵守 intent.md、spec.md、plan.md、tasks.md、code-review.md 和项目规则；
- 只修改 plan.md 明列且与红灯或目标测试直接相关的实现路径；
- 不弱化、改写、删除或跳过原断言来制造绿灯；
- 每处修改映射回具体红灯和规格场景；
- 同一测试转绿后，依次跑定向、模块、全量测试和静态检查/构建；
- 再用 {{真实文件/实际入口/本地容器/dry-run}} 验证实际接线；
- 在分层测试前完成 AI 自审和人工 Code Review，填写 `code-review.md`；评审未通过不得继续；
- 对失败分类说明：本次回归、既有不稳定、环境问题；
- 检查最终 diff、工作区和产物，清理临时对象；
- 更新 tasks.md 的机器证据，不替人工勾选验收项；
- 未经另行授权，不提交、不推送、不切换分支、不合并、不部署。

若范围扩大、规格变化、真实入口未命中新逻辑或出现稳定回归，立即停止并转黄/转红报告。
```

## 多个变更点的拆分调查

```text
对工单 {{工单号}} 中的每个变更点分别建立证据，不把多个目标揉成一次修改。

规则：
- 一项变更至少对应一个可重复失败的目标断言和独立红灯/目标测试编号；
- 编译失败、夹具错误、依赖或环境故障不算任务证据；
- 无法复现或无法测试的项从“已确认任务”清单剔除或转黄；
- 每处实现修改必须映射到具体红灯或目标测试；
- 禁止无测试支撑的顺手修改；
- 每项分别判定入口风险；任一项命中红色排除项即拆出并转人工；
- 最后增加真实入口验证，防止底层测试绿但接线错误。

先只完成调查和红灯/目标测试，不修改实现代码。汇报表格列出：变更点、入口灯色、测试证据、原因或实现依据、影响范围、建议修改、需人工决定事项。
```

## 外部系统语义验证

```text
我怀疑 {{语法/API/数据库行为}} 不兼容，但这只是待验证假设。

请先核对项目规则和工单文档，并分两条证据链：
1. 在代码仓库中建立红灯回归测试；
2. 在已批准的本地 {{容器/模拟服务/临时库}} 中实测原写法和候选写法。

覆盖 spec.md 要求的正向、负向、空值、单元素、多元素和特殊字符场景。若实测推翻原判断，以实测结果为准，不删除或改写原本正确的语义。临时对象用完清理，不访问生产环境，不使用真实敏感数据。本轮只建立事实和方案，是否修改实现代码须人工确认。
```

## 黄灯转人工决策汇报模板

```text
状态：黄色，已停止继续修改。

- 工单：{{工单号}}
- 触发黄灯的条件：{{复现/夹具/环境/范围/业务口径/回归/接线/工作区}}
- 已完成：{{只读调查、测试、命令}}
- 已确认事实：{{有证据的结论}}
- 尚未确认：{{假设或缺口}}
- 当前工作区：{{新增/修改文件、是否有实现代码改动}}
- 可选方案：{{方案、影响范围、风险和验证办法}}
- 需要人工决定：{{明确问题}}

在获得书面确认和更新后的绿色路由前，不继续修改实现代码。
```
