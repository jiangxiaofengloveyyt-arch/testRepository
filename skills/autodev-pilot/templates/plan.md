## 两阶段执行

### 阶段一 调查与红灯

1. 沿真实入口追踪到最小实现路径，记录调用链和影响范围。
2. 构造最小但忠于现场的夹具或目标场景，保留触发关系，不复制无关业务内容。
3. 先只修改测试，运行测试并确认失败发生在 `{{预期目标断言}}`。
4. 将失败分类为：已确认功能失败、测试自身错误、环境故障、既有不稳定或无关失败。
5. 若不是有效红灯或目标行为测试，停止；不得修改实现代码，不得把猜测列为已确认需求或缺陷。

阶段一产物：测试文件、红灯/目标测试命令与失败摘要、原因假设、影响范围、最小实现建议、更新后的入口灯色。

### 阶段二 最小实现与转绿

仅在入口灯色为绿色且有效红灯或目标测试经人工确认后执行：

1. 只修改红灯或目标测试证明相关的实现路径。
2. 不改变或弱化原红灯/目标断言，不用删除测试、跳过测试或扩大容差制造绿灯。
3. 每处实现修改标注对应测试编号。
4. 运行同一红灯或目标行为测试并确认转绿。
5. 补齐规格要求的正向、负向和边界测试。
6. 依次执行定向、模块、全量测试和静态检查/构建。
7. 通过真实文件、实际入口、本地容器或 dry-run 验证生产接线。
8. 检查最终 diff、工作区、产物和范围，清理临时对象。

## Code Review 计划

### AI 自审

实现完成后，AI 必须对照 `intent.md`、`spec.md`、`plan.md` 和最终 Diff 自审，至少检查：范围越界、规格一致性、红灯/目标测试映射、异常处理、安全、性能、并发、兼容性、真实接线和敏感信息。

### 人工 Code Review

人工评审人在分层测试前独立检查 `code-review.md`。评审重点包括：

- 每处实现修改是否有红灯或目标测试支撑。
- 是否弱化、删除、跳过测试，或通过改规格制造绿灯。
- 是否存在无关修改、顺手重构、外部契约变化或高风险逻辑。
- 测试是否可能绕过真实入口、配置、容器或外部系统语义。
- Diff、工作区、日志、提交说明和证据是否干净、可追溯、已脱敏。

评审结论为“退回”时，先修复阻断项并重新评审；评审结论为“转黄/转红”时，不进入自动化测试和提交阶段。

## 外部语义验证

若问题涉及数据库语法、API 或第三方行为，但仍经人工判定适合试点，必须分两条证据链：

1. 代码仓库内的红灯回归测试。
2. 本地容器、模拟服务或临时库中对原写法与候选写法的实测。

至少覆盖规格中适用的正向、负向、空值、单元素、多元素和特殊字符场景。实测推翻原假设时，以实测为准，保留原本正确语义并转黄复核。临时对象须清理，不得使用生产环境或真实敏感数据。

## 停止和升级条件

出现以下任一情况立即停止，将入口灯色改为黄色或红色并报告：

- 有效红灯或目标行为测试无法建立或不能重复。
- 实现需要改变已冻结规格或弱化断言。
- 修改扩展到表外文件、跨模块、外部契约、数据结构或高风险业务。
- 全量测试出现稳定失败，无法证明为既有不稳定或环境故障。
- 真实入口未命中新逻辑，出现“单元测试绿但生产接线旧”的情况。
- 需要下载未知依赖、提升权限、访问外部系统、使用敏感数据或执行生产操作。
- 发现来源不明或与本次重叠的工作区修改。

## 权限边界

- 允许：只读检索、读取项目规则、在批准范围内编辑测试和实现代码、执行批准的本地测试与检查。
- 需另行明确授权：安装依赖、访问外部系统、启动有成本的服务、提交、推送、切换分支、合并、发布、部署。
- 禁止自动执行：生产写操作、不可逆数据变更、输出密钥/Token/真实个人或客户信息、覆盖或回退他人修改。
