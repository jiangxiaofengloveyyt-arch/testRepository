#### 1.1.2 需求背景

现有系统仅支持预算编制结果录入，即用户可以在预算总表中录入最终预算结果，但预算结果形成前的任务下发、子表填报、独立审批、汇总取数、退回修改和审批前调整等过程主要在线下完成。

当前业务存在以下问题：

| 问题        | 现状                          | 业务影响              |
| --------- | --------------------------- | ----------------- |
| 缺少编制任务管理  | 预算任务、责任部门、填报人员及时间要求主要依靠线下传达 | 难以统一掌握编制进度和责任归属   |
| 缺少子表过程管理  | 各业务条线通过独立表格编制预算             | 版本分散，数据来源难追溯      |
| 缺少子表独立审批  | 子表审批与预算系统未形成闭环              | 已审批数据与实际汇总数据可能不一致 |
| 缺少自动汇总过程  | 子表结果需要人工汇总至总表               | 易发生漏项、错填和重复录入     |
| 缺少审批前调整能力 | 总表被驳回后，子表修改和总表更新依赖线下协调      | 调整过程不透明，重新汇总效率低   |
| 总表与子表状态割裂 | 无法判断总表数据对应哪个子表审批版本          | 结果可信度和追溯性不足       |

#### 1.1.3 业务目标

1. 建立“预算任务—子表填报—子表审批—总表汇总—总表审批”的完整预算编制闭环。
2. 确保总表中来源于子表的数据均来自有效的子表审批结果，并能够追溯来源。
3. 支持总表审批通过前的子表调整、重新汇总和总表重新审批。
4. 保留原预算编制结果录入总表及其既有业务逻辑，使新过程最终汇聚到原总表。
5. 总表审批通过后的变更继续使用现有“预算调整”功能，不在本次重复建设。

#### 1.2.3 新旧模块业务边界

| 业务事项      | 原结果录入模块                            | 本次过程管理                                  |
| --------- | ---------------------------------- | --------------------------------------- |
| 预算总表内容    | 保留，仍为最终预算结果载体                      | 将已审批子表结果汇聚至该总表                          |
| 总表手工填写科目  | 保留原填写和计算规则                         | 不改变原业务口径                                |
| 子表任务下发    | 不支持                                | 本次新增                                    |
| 子表填报与审批   | 不支持                                | 本次新增；同一张子表可配置多名填报人，按暂存版本进行并发控制          |
| 子表向总表汇总   | 不支持完整过程                            | 本次新增                                    |
| 总表审批前调整   | 缺少完整过程                             | 本次新增                                    |
| 总表审批      | 沿用既有审批规则                           | 增加提交前的子表完整性检查                           |
| 总表审批通过后调整 | 使用现有“预算调整”                         | 不新增平行调整入口                               |
| 既有预算模板    | 保留模板主数据、预算科目树、超预算标识和 SpreadJS 模板文件 | 作为过程模板设计的候选基础；不直接以可变的既有模板记录作为已下发任务的运行依据 |
| 历史已完成预算   | 按原方式查询和使用                          | 不强制补录历史编制过程                             |

过程任务与原总表的衔接规则：

1. 任务下发时，系统为该任务创建或绑定一份原“预算编制结果录入”总表，并记录唯一关联关系；该总表即任务的最终结果载体，不另建平行总表。
2. 同一预算年度、编制主体和组织范围内，只允许存在一个未作废的预算编制任务。集团、公司、项目等不同组织层级可分别建立任务；存在已配置的上下级额度分配关系时，下级任务须受上级可用额度约束，未配置时各层级任务独立且不自动向上汇总。
3. 存在预算编制任务时，原总表的直接编制入口不得绕过任务流程；用户应进入对应任务处理。任务未建立时，保留原直接编制总表能力。
4. 如任务绑定已有未提交的原总表草稿，原草稿中的手工科目继续保留；配置为子表来源的科目以汇总规则重算并覆盖，系统须在下发前向预算管理员确认该处理结果。
5. 既有预算模板可被选择为过程模板的基础来源；但只有完成过程模板补充配置、发布校验并形成发布版本后，才可用于新任务下发。已下发任务只能读取其下发时固化的模板、科目和规则快照，不读取既有模板后续编辑结果。

#### 1.2.4 页面与导航范围

本次功能沿用现有系统导航和账号权限体系，在现有“预算管理”下新增“预算编制过程”分组。以下五项为本期确认的可见业务菜单；不为 BPM 新建编制业务菜单。

| 菜单层级 | 页面职责 | 可见角色 |
|---|---|---|
| 预算管理 / 预算编制过程 / 编制任务 | 创建、下发、查询和跟踪任务；按状态和异常筛选进入任务详情、子表和总表 | 预算管理员、任务责任人、被分工人员 |
| 预算管理 / 预算编制过程 / 过程模板与规则 | 管理过程模板版本、填写区、同业务条线依赖、汇总规则及发布校验 | 预算管理员 |
| 预算管理 / 预算编制过程 / 额度分配与控制 | 维护总部至事业部/项目的逐级额度、可用额、占用和超额控制 | 预算管理员 |

子表填报、总表汇总、调整管理、版本历史和过程追溯均为以任务为上下文的隐藏页面，不占用一级、二级或三级菜单。用户由任务列表或任务详情进入，完成后返回任务详情或来源页面：

| 隐藏页面 | 入口与返回 | 业务边界 |
|---|---|---|
| 任务详情 | 任务列表 | 展示任务全貌、子表/总表状态、分工和过程操作；作废申请仅在此处发起 |
| 子表填报 | 任务详情；返回任务详情 | 仅填报、校验、暂存、提交和查看本子表；审批查看通过 BPM 链接进入 |
| 总表汇总 | 任务详情；返回任务详情 | 汇总来源项、填写手工项、手动/定时重算、完整性检查和总表提交 |
| 调整管理 | 子表状态、依赖过期异常或任务详情；返回子表/任务详情 | 创建调整稿、重算依赖区、查看差异并提交调整审批 |
| 过程追溯 | 任务详情中的“过程追溯”；关闭后返回任务详情 | 查询任务事件、版本、汇总批次、科目来源和审批结果，不作为独立菜单 |

审批待办、审批人、审批节点和审批顺序继续在既有 BPM 中管理。子任务、总表材料就绪或任务作废申请创建后，过程页面仅提供“打开审批页面”操作；打开链接不代表审批已发起或完成。

#### 1.2.5 状态模型与展示规则

本期所有页面、接口和过程记录均须将**业务状态**与**审批状态**分字段保存和展示，禁止以“总表审批中”“审批驳回”“作废审批中”等组合名称作为任务、子表或总表的业务状态。

| 维度 | 适用对象 | 说明 |
|---|---|---|
| 业务状态 | 预算任务、子表、总表、调整稿 | 表示对象处于创建、编制、可提交、已提交、有效、完成、作废或依赖过期等业务阶段，由编制业务处理并驱动可操作范围 |
| 审批状态 | 每一笔子表、总表、任务作废审批申请 | 只表示 BPM 对该笔审批申请的处理结果；不得覆盖对象业务状态或有效版本 |

审批状态统一使用以下标准值：

| 审批状态 | 含义 | 对业务对象的影响 |
|---|---|---|
| 未审批 | 审批材料已封存，但尚未确认在 BPM 中实际发起 | 提交快照只读；可按当前规则取消本轮 |
| 审批中 | BPM 已确认实际发起，尚未产生终态 | 提交快照只读；仅可按 BPM 权限撤回 |
| 审批通过 | BPM 已给出通过结果 | 由对应业务服务复核后生效新子表版本、正式总表或任务作废 |
| 审批拒绝 | BPM 已拒绝该审批申请 | 本轮审批历史保留；初次子表/总表恢复到可编辑或待提交业务阶段，调整继续保留原有效版本 |
| 审批退回 | BPM 退回发起人，或发起人撤回成功 | 本轮审批历史保留；恢复到可编辑或待提交业务阶段；“撤回”是操作，不单列为审批状态 |

页面至少同时展示“业务状态”和“最近一笔相关审批状态”。例如：`任务业务状态：总表待提交｜总表审批状态：审批拒绝`，或 `子表业务状态：有效但关键依赖过期｜最近审批状态：审批通过`。没有审批申请时，审批状态显示“—”，不得显示“未审批”。

### 1.3 干系人与使用用户角色

| 角色         | 主要职责                      | 主要关注点           |
| ---------- | ------------------------- | --------------- |
| 预算管理部门     | 制定预算编制安排、模板和管理规则；定义预算科目体系 | 过程可控、数据完整、结果可追溯 |
| 财务部门       | 管理总表科目、汇总口径和最终预算结果        | 科目口径一致、汇总结果准确   |
| 各业务条线及专业公司 | 填写本条线预算子表并说明测算依据          | 填报方便、计算准确、审批独立  |
| 预算管理员      | 创建任务、维护模板和规则、跟踪整体进度       | 任务覆盖完整、异常可发现    |
| 任务责任人（可多名） | 统筹一个预算任务的编制和总表提交          | 子表齐备、总表完整、按期完成  |
| 子表填报人      | 填写和修改被分配的预算子表             | 权限明确、数据不丢失、提示清晰 |
| 子表审批人      | 审核子表数据及测算结果               | 审批内容与提交版本一致     |
| 总表主责人      | 查看汇总结果、填写手工科目、提交总表审批      | 汇总完整、异常可定位      |
| 总表审批人      | 审核总体预算结果及子表依据             | 可查看来源，不能直接修改子表  |
| 查询与审计人员    | 查询过程、版本、审批和调整记录           | 过程可追溯、责任可识别     |

同一用户可以同时承担多个业务角色，其可见任务和可执行操作以现有账号权限及任务分工为准。

### 1.4 前置约束与现有系统约束

1. 原“预算编制结果录入”总表继续作为正式预算结果载体。
2. 现有系统导航、账号和权限体系继续使用。
3. 总表审批通过后的调整继续使用现有“预算调整”流程。
4. 总表和子表模板必须在任务下发前准备完成。
5. 主营公司与专业公司可以使用相同科目体系，但计算口径和模板可以不同。
6. 同一业态的项目原则上复用统一模板。
7. 本期预算基础数据由业务人员手工填写。
8. 子表之间允许存在单向数据依赖，但不强制规定填报顺序。
9. 存在循环依赖时，不支持自动闭环计算，应调整表单归属或改为手工填写。
10. 总表多人协作暂不采用单元格级分工，由总表主责人统一汇总录入。
11. 子表、总表及任务作废审批人由 BPM 流程定义；审批人通过审批时看到的材料必须与发起时封存的版本一致。
12. 任务覆盖集团、公司、项目等组织层级；不同层级任务独立编制、不自动汇总。预算年度内按月度管理，模板须明确月度数据的填写与年度汇总口径。
13. 本次调整不影响原有直接编制总表的功能。

## 2. 用户角色与业务场景

### 2.1 全部业务角色

| 角色         | 可处理对象        | 核心业务行为               |
| ---------- | ------------ | -------------------- |
| 预算管理员      | 全部预算任务、模板及规则 | 创建任务、配置子表、分配责任人、跟踪进度 |
| 任务责任人（可多名） | 被授权的预算任务     | 协调填报、检查完整性、管理总表      |
| 子表填报人      | 被分配的子表       | 填写、保存、提交、查看审批结果、发起调整 |
| 子表审批人（BPM） | BPM 待审批子表    | 查看提交快照、审批通过或驳回       |
| 总表主责人      | 被授权的总表       | 查看汇总、填写手工项、重算、提交审批   |
| 总表审批人（BPM） | BPM 待审批总表    | 查看总表及子表来源、审批通过或驳回    |
| 预算调整经办人    | 已生效预算        | 通过现有预算调整功能办理审批后变更    |
| 查询人员       | 授权范围内的任务和结果  | 查询状态、结果、版本及过程记录      |

### 2.2 主业务场景

#### 场景一：创建并下发预算编制任务

预算管理员选择预算年度、编制主体和适用模板，设置任务责任人（可多名）、子表范围、填报责任人及时间要求后下发任务。各责任人从任务列表按本人分工、任务状态和异常类型筛选进入待处理事项；BPM 审批待办仍在 BPM 中处理。

#### 场景二：业务条线独立填写并审批子表

子表填报人填写本条线预算测算数据。不同子表可以并行填写和独立审批，任一子表被驳回不影响其他子表继续流转。

#### 场景三：总表汇总并发起审批

已审批通过的子表成为有效取数来源。总表按照既定规则汇总子表数据；不来源于子表的科目由总表主责人按原结果录入逻辑填写。总表完整后发起审批。

#### 场景四：总表被驳回后调整子表

总表审批被驳回且驳回原因涉及子表时，相关填报人发起子表调整。调整审批通过后形成新的有效子表版本，总表重新汇总并再次提交审批。

#### 场景五：总表审批通过并形成正式结果

总表审批通过后，本次预算编制任务完成，原结果录入总表中的内容成为正式预算结果。后续如需调整，进入现有“预算调整”流程。

### 2.3 次要业务场景

1. 子表因依赖其他子表而暂时计算为零或不完整，填报人可先保存，审批人可根据业务合理性决定是否驳回。
2. 总表主责人主动重新汇总，检查最新审批子表是否已全部反映到总表。
3. 预算管理员复制已有模板形成新版本，并应用于新的预算任务。
4. 审批人查看子表提交时形成的Excel附件，核对多Sheet数据。
5. 查询人员追溯某个总表科目的来源子表、审批版本和最近调整记录。
6. 动态增加岗位、房号、项目或其他业务明细行，并自动纳入相关汇总范围。

### 2.4 明确不支持的业务场景

1. 总表审批通过后直接回到子表修改。
2. 未经审批的子表数据进入正式总表汇总结果。
3. 总表审批人直接修改子表数据。
4. 多人同时分别维护总表中的不同单元格。
5. 通过本期功能自动从合同、财务、收入或其他业务系统取得预算数据。
6. 强制要求存在依赖关系的子表按固定顺序填写。
7. 自动处理互相依赖的子表计算。
8. 在本模块中办理费用报销。
9. 对历史已完成预算反向补建完整的子表编制过程。
10. 上传本地 Excel 文件并导入为子表或总表草稿。

### 3.2 预算编制任务管理

#### 3.2.1 创建编制总任务

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 预算管理员创建一个年度预算编制任务，并确定其总表、子表及下发确认责任分工 |
| 业务输入 | 预算标题、年度、所属组织、业态、模板 |
| 预期输出 | 形成待下发的预算编制任务，包含一张总表和对应子表 |
| 业务规则 | 一个任务代表一个编制主体及组织范围在一个预算年度的一份完整月度预算；同一年度、编制主体和组织范围只允许一个未作废任务；任务只能选择已发布且适用范围匹配的过程模板及规则版本；任务下发前可修改，已下发后不得新增、删除、更换子表，也不得变更模板或取数规则 |

主要业务信息项：

| 信息项 | 必填 | 业务规则 |
|---|---:|---|
| 预算标题 | 是 | 在用户授权范围内应便于唯一识别 |
| 年度 | 是 | 应为系统允许开展编制的年度 |
| 所属组织 | 是 | 选择集团、公司或项目等组织层级及具体组织；不同组织范围任务独立，不自动汇总 |
| 业态 | 否 | 用于匹配预算模板和计算口径 |
| 模板名称 | 是 | 对应预算模板 |

任务创建时，系统须校验同一预算年度、编制主体和组织范围内不存在未作废任务；已作废任务保持只读，不计入该校验。
#### 3.2.2 下发任务

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 将已配置完整的预算任务发送给相关责任人 |
| 业务输入 | 待下发任务及其责任分工 |
| 预期输出 | 任务进入编制中，各子表责任人收到待办 |
| 业务规则 | 缺少已发布模板、责任人或编制时间时不得下发；下发时须固化子表/总表模板 JSON、科目、填写控制、依赖关系和取数规则快照；后续编辑既有预算模板或过程模板均不得影响已下发任务 |

成功提示：“预算编制任务已下发。”

失败提示应明确指出缺失项，例如：“子表‘人员成本’尚未配置填报人，无法下发。”

#### 3.2.3 任务状态

| 任务业务状态 | 进入条件 | 可执行业务行为 | 退出条件 |
|---|---|---|---|
| 待下发 | 任务创建完成 | 编辑任务、配置子表、下发、申请作废 | 成功下发或作废生效 |
| 编制中 | 任务已下发 | 子表填报、调整、汇总和查看进度；满足条件后进入总表待提交 | 必填子表满足总表汇总条件、总表待提交或作废生效 |
| 总表待提交 | 必填子表满足汇总要求，或总表审批申请被拒绝/退回 | 汇总、填写总表手工项、提交审批、申请作废 | 总表审批通过、重新进入编制中或作废生效 |
| 已完成 | 总表审批通过 | 查询、追溯、进入现有预算调整 | 无 |
| 已作废 | 任务作废审批通过且编制业务已完成作废处理 | 查询、追溯、查看补偿任务关联 | 无 |

任务只能在待下发、编制中或总表待提交状态由预算管理员**申请作废**，不得通过预算编制页面直接将任务置为已作废。申请前，任务关联的子任务与总表审批必须均为审批通过、审批拒绝或审批退回；存在未审批或审批中的审批申请时，系统应拒绝作废申请并定位待处理申请。申请必须跳转现有 BPM 的 `TASK_VOID` 流程，并填写作废原因；申请期间不改变任务业务状态，但 `voidFrozen=true`，任务、子表、总表与调整均冻结为只读，不得产生新的编制提交；页面单独展示任务作废审批状态。

只有 BPM 返回“作废审批通过”后，编制业务才执行作废：原任务、子表、总表和过程记录永久只读，未完成编制待办失效，原任务不再计入唯一性校验。系统在同一业务处理内为预算管理员创建一条新的“待下发补偿编制任务”待办，并生成一个独立的新任务草稿：默认复制原任务的年度、组织范围、编制主体、模板快照、子表范围、分工及时间配置，记录原任务为补偿来源；不复制草稿数据、审批快照、审批实例、调整稿或总表结果。管理员核对或修改新草稿后自行下发，系统不得自动下发。

任务作废审批状态为审批拒绝或审批退回时，解除 `voidFrozen` 并保留原任务业务状态和既有数据，不得创建补偿任务。作废后不提供“撤销作废”或窗口期；误作废只能通过上述补偿新任务重新编制，不能恢复原任务。

### 3.3 子表填报

#### 3.3.1 子表独立管理

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 按业务条线或专业公司管理相互独立的预算编制子表 |
| 业务输入 | 子表模板、任务主体、填报责任人和预算年度 |
| 预期输出 | 形成可独立填报、审批和调整的子表实例 |
| 业务规则 | 同一业务条线可以包含多张子表；各子表的数据、审批和调整互不覆盖；一张子表可以包含多个Sheet |

子表应清晰展示：

- 所属预算任务；
- 预算年度；
- 所属组织
- 任务名称及业务条线；
- 任务状态；
- 责任人；
- 当前版本；
- 创建/更新时间；
- 提交和审批记录；

同一子表配置的填报人均可基于当前草稿版本暂存、提交、撤回初次提交和发起调整；提交或调整时再次校验其填报权限及当前版本。

#### 3.3.2 表格填报行为

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 填报人在子表中填写预算测算数据，并查看自动计算结果 |
| 业务输入 | 标准参数、业务明细、人数、数量、金额、比例及其他模板规定内容 |
| 预期输出 | 形成完整、可校验、可提交的子表预算数据 |
| 业务规则 | 人工填写区域与自动计算区域应明显区分；自动计算内容不可被普通填报人直接覆盖；未通过校验的数据不得提交审批 |

业务规则：

1. 一张子表可包含多个Sheet，各Sheet共同构成一次提交内容。
2. 填报人只能编辑被授权子表中的可填写区域。
3. 公式计算区域、汇总区域和固定说明区域应保持只读。
4. 支持按业务需要增加或删除动态明细行。
5. 新增明细行后，应自动纳入本子表的计算和汇总范围。
6. 保存草稿不等于提交审批。
7. 子表提交前应检查必填内容、数据格式和业务勾稽关系。
8. 子表数据、模板引用、取数来源和依赖关系均按“预算年度＋业务条线/专业公司＋组织范围”隔离；禁止跨业务条线或跨专业公司直接引用、计算、覆盖或汇总子表数据。总表仅能按已发布的本条线来源规则汇总对应子表结果。
9. 依赖其他子表的数据缺失时，不强制阻止保存；普通依赖缺失时，提交页和审批页均展示风险说明。允许的依赖仅限于同一业务条线/专业公司及任务范围内的子表。
10. 任务配置为关键依赖时，关键依赖仅在依赖子表存在当前审批通过的有效版本时视为满足；草稿、审批中版本和已驳回版本均不得作为关键依赖数据。关键依赖未满足应阻止该子表提交，并定位缺失的依赖对象。
11. 关键依赖子表调整审批通过后，依赖该数据的已审批下游子表须立即标记 `DEPENDENCY_STALE`，页面显示“关键依赖已过期，不能用于总表汇总”；在下游子表通过调整重新校验并审批前，任务不得提交总表。
12. 系统须为每个 `DEPENDENCY_STALE` 下游子表创建“关键依赖已过期需要重审的子表”异常事项；任务列表的异常筛选和任务详情须展示发生变化的上游子表、原依赖版本、当前应采用版本和“发起调整重审”入口。该异常不得由用户手工忽略或关闭。
13. 从异常事项或子表页面发起重审时，系统创建调整稿并默认带出该子表上一有效版本的数据；依赖区域必须按当前上游有效版本重新计算生成，保留非依赖人工填写区域，并向用户展示调整前后差异。用户确认后按调整审批规则提交，形成子任务调整审批；审批通过且再次校验依赖版本无误后，才解除 `DEPENDENCY_STALE` 并恢复为总表可用来源。
14. 重审草稿或审批期间，上游关键依赖再次变化时，系统须重新标记该草稿或提交版本为依赖过期，并要求基于最新依赖重新生成调整稿；不得以旧依赖版本审批后直接恢复总表取数资格。
15. 双向依赖不得作为自动计算规则投入使用。

#### 3.3.3 保存与版本冲突

1. 同一张子表可配置多名填报人；多人可以同时打开并填写，但系统不保留编辑锁，也不处理异常锁释放。
2. 用户必须通过“暂存”保存草稿；未暂存即离开页面的填写内容不予保存。
3. 暂存时系统校验草稿版本。以先成功暂存的版本为当前版本；后暂存的用户如基于旧版本，系统不得覆盖当前版本，应提示重新加载。
4. 保存失败时，不得向用户展示“保存成功”；应保留当前填写内容并提示重新保存。
5. 用户打开旧版本后，不得直接覆盖更新版本。

成功提示：“子表草稿已保存。”

版本冲突提示：“该子表已产生新版本，请刷新后基于最新版本继续处理。”

### 3.4 子表独立审批

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 每张子表独立提交审批，不受其他子表审批状态影响 |
| 业务输入 | 已完成校验的子表数据及提交时的完整内容 |
| 预期输出 | 形成固定审批版本，并记录独立的子表业务状态和标准审批状态 |
| 业务规则 | 每次提交应形成固定审批版本；审批过程中原版本不可修改；审批状态仅作用于本次审批申请，业务状态决定版本是否可编辑和是否可作为总表来源 |

#### 3.4.1 正常流程

```text
填报人完成子表
  ↓
执行提交前校验
  ├─ 校验不通过 → 标识问题位置，返回修改
  ├─ 依赖数据不完整 → 显示风险说明，按业务允许情况继续或返回
  └─ 校验通过 → 生成本次提交内容和Excel附件
                         ↓
                      创建审批申请
                         ↓
                 审批人查看提交版本
                  ├─ 审批通过 → 该版本成为有效取数来源
                  ├─ 审批拒绝 → 本轮历史保留，返回填报人修改
                  └─ 审批退回 → 本轮历史保留，恢复至可处理状态
```

#### 3.4.2 子表业务状态与审批状态

| 子表业务状态 | 最近一笔相关审批状态 | 用户可见表现 | 编辑规则 | 后续行为 |
|---|---|---|---|---|
| 草稿 | —，或历史审批拒绝/审批退回 | 显示“待填报”或“待提交”；历史结果另行展示 | 可编辑 | 保存、提交 |
| 已提交 | 未审批或审批中 | 显示本轮审批状态 | 提交快照不可编辑 | 查看审批；审批中可按 BPM 权限撤回 |
| 有效 | 审批通过 | 显示通过时间和有效版本 | 有效版本只读 | 供总表取数；需要修改时发起调整 |
| 调整草稿 | 最近有效版本为审批通过；调整申请尚未提交 | 显示调整原因、差异及原有效版本 | 原有效版本只读，调整稿可编辑 | 提交调整审批 |
| 调整已提交 | 未审批或审批中 | 显示本次调整审批状态 | 调整提交版本只读 | 查看审批；审批中可按 BPM 权限撤回 |
| 有效但关键依赖过期 | 最近有效版本为审批通过 | 显著展示“关键依赖已过期，不能用于总表汇总”及上游版本 | 当前有效版本只读；仅可发起调整重审 | 默认带出上一有效版本并按最新依赖重算；新调整审批通过后恢复有效 |
| 已作废 | — | 显示任务作废关联 | 全量只读 | 仅查询与追溯 |

#### 3.4.3 审批内容要求

1. 审批人查看的内容必须与填报人提交时的内容一致。
2. 审批附件应包含当前子表全部Sheet及提交时数据。
3. 审批中对模板或其他子表的修改，不得改变本次提交内容。
4. 审批通过后，该版本成为总表的有效取数来源。
5. 审批拒绝或审批退回后，应向填报人展示 BPM 返回原因。
6. 调整审批状态为审批拒绝或审批退回时，原已审批有效版本继续有效。
7. 发起人可按现有审批流程的撤回权限，在审批结果产生前撤回子表或调整审批。撤回成功后，该轮审批状态为审批退回；初次提交的子表恢复草稿且不产生有效取数版本，调整撤回后原有效版本继续用于总表取数。

撤回操作应保留撤回人、时间、原因和原提交版本，并同步关闭原审批待办。

### 3.5 总表汇总

#### 3.5.1 汇总取数

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 将已审批通过的子表数据按预算科目汇总到原预算结果录入总表 |
| 业务输入 | 有效子表版本、总表模板、科目取数规则、总表手工填写数据 |
| 预期输出 | 形成来源清晰、计算完整的预算总表 |
| 业务规则 | 仅已审批通过的子表可以成为正式取数来源；同一科目可在不同总表模板中使用不同取数逻辑 |

业务规则：

1. 总表与子表共同构成一份完整预算。
2. 总表按预算科目展示汇总结果。
3. 来源于子表的科目应按有效取数规则形成结果。
4. 不来源于子表的科目继续使用原结果录入逻辑，由总表主责人填写。
5. 来源于子表的结果在总表中不可直接修改。
6. 如需修改子表来源数据，必须回到对应子表办理审批前调整。
7. 总表应允许查看每个汇总科目的来源子表、有效版本及汇总结果。
8. 子表调整审批通过后，相关总表科目应更新为新有效版本结果。
9. 更新不得覆盖总表主责人已填写的无关手工科目。
10. 总表提交审批前，应完成一次完整性检查。
11. 若存在未审批必填子表、未审批的取数来源、失效规则或汇总失败科目，应明确标识，不得静默按零处理。

#### 3.5.2 多模板取数

1. 取数规则按“总表模板＋预算科目”分别管理。
2. 同一预算科目在主营公司与专业公司总表中可以具有不同取数逻辑。
3. 修改一个模板的取数规则不得影响其他模板。
4. 同一总表模板的同一预算科目只能有一套当前有效取数规则。
5. 已下发任务应保留任务采用的规则版本，规则变化不得无提示改变历史审批结果。
6. 规则失效或来源子表停用时，应阻止产生不可识别的汇总结果。
7. 一条总表科目规则可配置一个或多个来源；每个来源须明确子表、Sheet、取数区域或命名项、期间字段、筛选条件、汇总方式、精度与舍入规则。
8. 多来源汇总前须按规则合并；同一来源记录不得被重复计入。来源为空、筛选无结果或取数精度不匹配时，按规则标识为“无有效来源”并阻止总表提交，不得默认按零处理。
9. 汇总方式至少应明确求和、取值、平均或公式计算；月度值与年度值的关系须由模板或规则定义，年度汇总不得由系统自行猜测。

#### 3.5.3 总表完整性检查

提交总表前至少检查：

- 任务配置为必填的子表是否均已达到规定状态；
- 作为取数来源的子表是否审批通过；
- 每个自动汇总科目是否能够找到有效来源；
- 是否存在依赖数据缺失风险；
- 是否存在关键依赖版本已变化但下游子表尚未重新审批的情况；
- 是否存在未处理的子表调整；
- 是否存在汇总结果版本变化但尚未确认；
- 总表手工填写的必填科目是否完整；
- 总表内部业务勾稽关系是否满足原有规则。

完整性检查失败时，应列出具体子表、科目和原因，便于用户定位。对于 `DEPENDENCY_STALE`，总表页面须显示对应下游子表、发生变化的上游版本及“等待子表调整重审”的状态；总表主责人可跳转查看，但不能替代子表填报责任人关闭该异常。

#### 3.5.4 重算触发与适用状态

系统应同时支持事件自动重算、手动重算和定时重算；三类重算均只读取当前有效子表版本与当前任务快照中的规则，不得修改已提交的总表审批快照。

| 类型 | 触发时机 | 适用任务状态 | 处理规则 |
|---|---|---|---|
| 事件自动重算 | 子表初次审批通过、调整审批通过，或有效取数来源状态发生变化后 | 编制中、总表待提交 | 系统创建新的可核对汇总结果，并标记总表“结果已变化待确认”；不得自动提交总表审批 |
| 手动重算 | 总表主责人在总表页面点击“重新汇总” | 编制中、总表待提交 | 立即按当前有效来源和规则重算，展示来源与结果差异；同一任务已有重算执行时提示稍后重试 |
| 定时重算 | 每日 02:00 由系统定时任务扫描需重算任务；执行时间由系统参数配置 | 编制中、总表待提交，且存在来源变化、上次重算失败或管理员标记待核对 | 与手动重算使用相同规则和完整性校验；无变化任务不重复生成汇总版本；失败须记录原因，并在任务列表异常筛选和任务详情展示 |

总表存在审批状态为未审批或审批中，或任务作废申请审批状态为未审批或审批中，以及任务已完成或已作废时，不执行手动或定时重算；若审批中发现来源变化，仅记录“存在新来源待后续处理”，不得改写当前审批材料。总表审批状态变为审批拒绝或审批退回后，回到总表待提交并允许按上述规则重新汇总。

### 3.6 总表审批

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 总表主责人在汇总和校验完成后提交总表审批 |
| 业务输入 | 当前总表、有效子表来源及总表手工填写内容 |
| 预期输出 | 总表审批通过并形成正式预算结果，或被驳回后返回调整 |
| 业务规则 | 总表提交时形成固定版本；审批人可查看总表及子表依据，但不能修改子表数据；总表业务状态与审批状态独立保存和展示 |

| 总表业务状态 | 最近一笔总表审批状态 | 用户可执行操作 | 状态变化规则 |
|---|---|---|---|
| 可编辑 | —，或历史审批拒绝/审批退回 | 汇总、填写手工项、完整性检查 | 检查通过后进入总表待提交 |
| 总表待提交 | —，或历史审批拒绝/审批退回 | 重新汇总、暂存、检查、提交 | 创建审批快照后进入已提交 |
| 已提交 | 未审批或审批中 | 查看审批、查看快照；审批中可按 BPM 权限撤回 | 审批通过后任务完成；审批拒绝或审批退回后回到总表待提交 |
| 已生效 | 审批通过 | 查看、追溯 | 任务业务状态同步为已完成，后续变更进入既有预算调整 |
| 已作废 | — | 查询、追溯 | 任务作废后全量只读 |

#### 3.6.1 正常流程

```text
总表主责人完成汇总及手工填写
  ↓
执行完整性检查
  ├─ 检查失败 → 展示缺失项，返回处理
  └─ 检查通过 → 提交总表审批
                    ↓
               审批人审核
          ├─ 审批通过 → 形成正式预算结果，任务完成
          ├─ 审批拒绝 → 返回总表待提交
          └─ 审批退回 → 返回总表待提交
```

#### 3.6.2 总表审批规则

1. 审批人只能查看子表及其审批结果，不得在总表审批环节修改子表。
2. 总表审批状态为审批中时，提交版本保持不变。
3. 总表审批状态为审批拒绝后，原拒绝版本保留供追溯。
4. 驳回原因仅涉及总表手工科目时，由总表主责人修改后重新提交。
5. 驳回原因涉及子表时，应通过调整管理形成新的子表有效版本，再更新总表。
6. 总表重新提交前必须再次完成完整性检查。
7. 总表审批通过后，预算编制任务进入“已完成”。
8. 总表审批通过后的任何变更，必须进入现有“预算调整”，不得从本次新增调整入口修改。
9. 总表提交时，系统须封存总表内容、手工科目版本、模板及取数规则版本、每个来源子表的有效版本和汇总时间，形成不可修改的总表审批快照；审批人查看的总表、来源明细和附件均以该快照为准。
10. 发起人可按现有审批流程的撤回权限，在审批结果产生前撤回总表审批。撤回后恢复为“总表待提交”，须重新完成完整性检查；撤回前的审批快照和待办保留供追溯。

总表审批状态为审批中时不得发起子表调整；如需调整，须先撤回总表审批或等待审批结果。

### 3.7 总表审批前的子表调整

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 子表初次审批通过后，在总表最终审批通过前办理数据调整 |
| 业务输入 | 待调整子表、调整原因、调整内容及当前有效版本 |
| 预期输出 | 调整审批通过后形成新有效版本，并更新总表相关科目 |
| 业务规则 | 调整不得直接覆盖原有效版本；调整审批通过前，总表继续保留原有效版本数据 |

#### 3.7.1 调整流程

```text
用户选择已审批子表
  ↓
检查总表状态
  ├─ 总表已审批通过 → 禁止本入口调整，引导进入“预算调整”
  ├─ 当前已有调整且审批状态为未审批或审批中 → 禁止重复发起
   └─ 任务处于“编制中”或“总表待提交” → 基于当前有效版本创建调整稿
                         ↓
                    填写调整内容和原因
                         ↓
                      提交审批
                ├─ 审批通过 → 新版本生效，总表更新
                ├─ 审批拒绝 → 原版本继续有效，可修改后重提
                └─ 审批退回 → 调整稿恢复可处理
```

#### 3.7.2 调整规则

1. 只有已审批通过的子表可以发起调整。
2. 调整必须基于当前有效版本。
3. 同一子表同一时间只允许存在一个进行中的调整申请。
4. 调整审批通过前，原有效版本继续作为总表取数来源。
5. 调整审批通过后，新版本替代旧版本成为有效来源。
6. 总表应标记发生变化的科目，并提示总表主责人重新核对。
7. 调整审批状态为审批拒绝或审批退回不影响原有效版本。
8. 总表审批通过后，本入口不可再发起调整，并提示进入现有“预算调整”。
9. 调整原因必填，且必须上传业务说明附件；调整审批人应能查看调整前后差异、原因及附件。
10. 总表处于“审批中”时不得发起子表调整；如需调整，应先撤回总表或等待审批结果。

11. 任务已作废时不得发起或继续处理调整；调整中的草稿和审批待办随任务作废失效并保留记录。

#### 3.7.3 关键依赖过期后的强制调整重审

1. `DEPENDENCY_STALE` 不是普通提示，而是阻断总表取数与总表提交的业务状态；原已审批版本保留追溯，但不再作为可用汇总来源。
2. 子表页面在标题、状态标签和提交区显著展示“关键依赖已过期，不能用于总表汇总”，同时展示变化的上游子表、原版本、最新有效版本和发生时间。
3. 任务列表将该事项归类为“关键依赖已过期需要重审的子表”，支持按异常优先级筛选并在任务详情中置顶展示。上游发生多次变化时，同一子表合并为一个未关闭异常，内容更新为最新版本。
4. 用户只能通过“发起调整重审”创建处理该异常的调整稿，不允许直接编辑旧有效版本、直接重新提交初次审批或标记异常已处理。调整稿默认复制上一有效版本数据，依赖区按最新依赖数据重新计算；系统生成依赖变化前后差异和重审说明，作为调整审批材料的一部分。
5. 调整审批通过后，系统再次核对快照中的依赖版本均为当前有效版本；校验通过才关闭异常、清除 `DEPENDENCY_STALE` 并恢复总表取数资格。审批被驳回、撤回或再次过期时，异常继续保留，原版本仍不可用于总表。

### 3.8 模板与规则管理

#### 3.8.1 既有预算模板复用与过程模板边界

现有预算模板已经承担模板主数据、预算科目树、收支类型、超预算标识及 SpreadJS 文件的维护。本次不重建这些基础资产，但也不得直接把一条可随时编辑的既有模板记录用于已下发任务。

1. 既有预算模板可作为总表科目体系和 SpreadJS 初始文件的来源；既有科目树可继续用于总表预算科目、收支分类及超预算控制的基础配置。
2. 过程模板是面向预算编制过程的发布产物，除复用上述基础资产外，还须配置子表/总表角色、填写与只读范围、动态行、月度期间、校验、依赖和取数规则。
3. 既有预算模板编辑仍可服务于未被过程任务引用的普通预算业务；对于已被过程任务引用的模板基础，系统不得通过模板编辑自动更新任务、草稿、已提交版本、有效版本或审批快照。
4. 既有模板如未补齐过程元数据或未通过发布校验，只能继续按原预算模板用途使用，不能被选择为过程任务的子表或总表模板。
5. 既有模板维护中的批量维护、导入、导出和 SpreadJS 文件编辑属于模板资产维护，不构成也不替代任务草稿的 Excel 导入能力。

#### 3.8.2 子表过程模板

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 管理不同业务条线和专业公司的预算子表结构及计算口径 |
| 业务输入 | 模板名称、适用范围、基础模板来源、版本、Sheet、填写区域、只读/计算区域、参数区、动态行范围、月度期间定义 |
| 预期输出 | 形成可用于预算任务的有效子表模板 |
| 业务规则 | 模板采用“草稿—已发布—已停用”状态；已发布版本不可覆盖编辑，修改必须复制形成新版本；已被任务使用的版本及其任务快照均不得修改；停用模板不得用于新任务 |

子表模板应支持：

- 一个模板包含多个Sheet；
- 对每个 Sheet 定义唯一标识、展示名称、顺序及用途，禁止仅以展示名称或固定 Sheet 名称判断模板类型、填写能力或只读能力；
- 以模板元数据区分人工填写、自动计算、只读、说明和依赖区域，并明确区域范围、可编辑条件、字段/业务主键及校验规则；
- 定义标准参数区、明细填写区和汇总区；
- 定义月度数据的填写位置、期间校验和年度汇总口径；
- 定义允许动态增加或删除行的区域、行样式、公式扩展规则和业务主键列；
- 定义业务校验规则；
- 记录与其他子表的数据依赖；
- 复制已有模板形成新版本时，完整复制 SpreadJS 模板文件、区域元数据、科目配置、依赖、校验和规则关联；新版本应有独立版本号、发布记录和适用范围；
- 停用不再使用的模板。

模板发布前应至少校验：模板文件可正常加载、Sheet 标识唯一、填写/只读/动态区域不冲突、引用的科目及依赖对象存在、动态行公式扩展规则有效，以及本期支持的公式和组件能力满足要求。

#### 3.8.3 总表过程模板与取数规则

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 基于既有预算科目体系管理总表手工项、自动汇总项及其子表取数关系 |
| 业务输入 | 总表过程模板、基础预算科目、来源子表、来源内容、筛选条件、汇总方式 |
| 预期输出 | 形成可用于总表汇总的有效业务规则 |
| 业务规则 | 同一科目在不同总表模板中可使用不同规则；模板及规则变化均应形成可追溯发布版本；任务下发时应一并冻结总表模板、科目快照和规则版本 |

规则发布前应确认：

- 来源子表存在且处于有效状态；
- 来源子表与目标总表处于相同业务条线/专业公司范围；
- 来源内容在子表中存在；
- 汇总科目在总表中存在；
- 不存在循环依赖；
- 同一模板同一科目不存在多套同时有效的规则；
- 规则适用范围与模板适用范围一致。

模板停用、删除或修改时，应先检查其是否被过程任务、任务快照、提交版本或审批快照引用：被引用的历史版本必须保留可读和可追溯能力；新任务不得再选择已停用版本。不得因清理模板资产导致历史任务无法打开、无法生成审批依据或无法追溯科目来源。

#### 3.8.4 上下级预算额度分配与控制

系统应支持总部向事业部（或上级组织）下发预算额度、事业部向项目继续分配额度的管理。额度分配属于模板与规则管理的一部分，按“预算年度＋预算科目＋上级组织＋下级组织＋期间”配置，并可随模板/规则版本发布。

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 管理总部、事业部和项目之间可分配预算额度，并控制下级分配与编制提交不超过上级可用额度 |
| 业务输入 | 预算年度、上级组织、下级组织、预算科目、月度/年度额度、适用模板/规则版本、生效状态 |
| 预期输出 | 形成可追溯的额度分配链路、已分配额、已占用额、可用额及超额校验结果 |
| 业务规则 | 下级累计分配额不得大于上级可用额度；下级任务提交时，按映射科目和期间占用额度，不得超额；额度规则与任务模板快照一起冻结 |

业务规则：

1. 总部、事业部和项目可按实际组织层级逐级分配；不要求每个层级均存在，但每条分配记录必须有唯一的上级额度来源。
2. 同一上级组织、预算年度、科目和期间下，所有有效下级分配额之和不得超过上级可分配额度；保存、发布、下发和提交均须校验。
3. 项目或下级组织提交子表/总表时，系统按额度规则映射对应预算科目和期间，校验“本次占用额＋已有有效占用额”不超过可用额度；超额时阻止提交并展示上级额度、已分配/已占用额、本次金额和超额差额。
4. 为避免多个下级同时提交造成超额，同一额度范围的提交校验和额度占用必须以一次原子业务操作完成。审批状态为审批拒绝、审批退回或取消的未生效占用应释放；审批通过的额度占用转为有效占用。调整审批须以原有效占用为基础重新校验差额，不得重复占用。
5. 上级额度调整、下级分配调整和额度规则变更必须留痕、形成版本；已下发任务继续使用下发时冻结的额度规则。涉及已提交或已审批任务时，不得静默改变历史占用结果。
6. 未配置额度规则的任务不执行额度限制；配置后，相关任务和总表应展示额度来源、可用额度及校验结果。

### 3.9 过程追溯

| 项目 | 业务要求 |
|---|---|
| 功能描述 | 查询预算数据从填报、审批到汇总和调整的完整业务过程 |
| 业务输入 | 任务、子表、总表、科目、人员、时间或版本等查询条件 |
| 预期输出 | 展示关键操作、审批结果、版本变化及总表数据来源 |
| 业务规则 | 查询人员只能查看授权范围；记录应按业务发生顺序展示；已完成记录不得被普通用户修改 |

至少应记录：

- 任务创建、修改和下发；
- 子表填报和提交；
- 子表审批通过、驳回和撤回；
- 子表调整发起及审批结果；
- 总表汇总和重新汇总；
- 总表手工项修改；
- 总表提交、审批通过、驳回和撤回；
- 模板与取数规则的启用、变更和停用；
- 额度下发、分配、占用、释放和超额校验；
- 各总表科目对应的来源子表和有效版本。

### 3.10 任务交接

1. 人员离岗或组织调整时，预算管理员可对未完成任务调整任务责任人，不需要另行审批；任务责任人可配置一名或多名。需要时，管理员可同时调整总表主责人或子表填报责任人，但总表仍按既有规则由总表主责人统一汇总录入。
2. 交接本质是编制业务分工调整：须明确原责任人、新任务责任人（可多名）、交接范围、交接原因及生效时间，并保留审计记录。生效后，系统按新分工创建或回收本地编制待办和操作权限。
3. 交接不包含 BPM 审批待办转交，也不修改 BPM 审批人、节点、顺序或已发起流程实例；BPM 审批待办仍按 BPM 的既有授权与转办规则处理。本期不建设从预算任务交接自动同步到 BPM 的能力，页面须向管理员明确提示这一限制。
4. 已提交的子表和总表审批快照不因交接而改变；未完成的草稿、调整和本地编制待办按新分工处理。已在 BPM 中发起的子任务、总表或任务作废审批，其流程归属不因本地交接发生改变。

## 4. 业务数据需求

### 4.1 需要管理的业务数据

| 数据类别 | 业务内容 | 主要用途 |
|---|---|---|
| 预算编制任务 | 年度、组织范围、主体、责任人集合、编制期限、任务业务状态、作废冻结标识、补偿来源任务 | 界定一轮预算编制范围，并追溯误作废后的补偿新任务；作废审批状态由独立审批申请保存 |
| 任务分工 | 子表、业务条线、填报人、任务/总表责任人、有效期 | 明确本地编制责任和待办；不保存 BPM 审批责任 |

| 总表过程模板 | 基础科目、手工填写项、自动汇总项、单元格/科目范围 | 承载正式预算结果的过程配置 |
| 子表过程模板 | Sheet 标识与结构、参数、明细、填写/只读/计算/依赖区域、动态行和汇总内容 | 统一业务填报口径并控制表格行为 |
| 模板与规则发布版本 | 版本号、基础模板来源、适用范围、发布状态、完整配置、发布记录 | 保证新任务选择确定口径，发布后不可覆盖编辑 |
| 任务模板快照 | 下发时的模板 JSON、科目、区域控制、动态行、依赖及取数规则版本 | 保证任务、提交和审批不受后续模板编辑影响 |
| 额度分配规则 | 上下级组织、预算年度、科目、期间、可分配额度、版本和生效状态 | 管理总部至事业部/项目的预算额度下发与逐级分配 |
| 额度占用记录 | 额度规则、任务/提交版本、占用金额、占用状态、释放或生效时间 | 防止并发提交和调整造成额度超额，并支持追溯 |
| 子表填报数据 | 参数、人数、数量、金额、比例、业务明细 | 形成预算测算依据 |
| 子表计算结果 | 工资、社保、公积金、福利等分类结果 | 供审批和总表汇总 |
| 取数规则 | 来源子表、来源内容、筛选条件、汇总方式、目标科目 | 建立子表与总表关系 |
| 审批数据 | 提交版本、审批快照、标准审批状态、审批意见和时间 | 每笔申请仅使用未审批、审批中、审批通过、审批拒绝、审批退回五种状态；认定有效数据版本 |
| 调整数据 | 调整前版本、调整内容、调整原因、调整业务状态、关联审批状态 | 管理审批前变更；调整稿状态不与审批状态混用 |
| 总表结果 | 月度与年度结果、子表汇总结果、手工填报结果、来源版本快照、总表业务状态、关联审批状态 | 形成正式预算；总表是否可编辑与审批结果分别判断 |
| 追溯记录 | 操作人、时间、事项、变更前后状态 | 支持审计与责任追踪 |

### 4.2 子表业务数据范围

以人员成本子表为例，包括但不限于：

1. 标准参数：最低工资、社保和公积金缴费基数及比例、企业年金、补贴、福利、成本月数等。
2. 业务维度：专业序列、岗位、项目、管理模式等。
3. 人员数据：合同编制人数、实际运营人数及各类缴纳或发放人数。
4. 薪酬数据：月薪、年终奖及其他薪酬标准。
5. 专项成本：福利、补偿、保险、工服、教育、慰问等成本。
6. 计算结果：年度人工成本、月度人均成本及各分类成本。
7. 动态明细：岗位、房号、项目、存量和增量等不固定行数据。
8. 期间数据：预算年度内各月的预算值、月度计算结果及年度汇总结果。

不同业务子表的具体业务信息项由对应模板确定。

### 4.3 总表业务数据范围

1. 预算科目层级及科目名称；
2. 科目责任归属；
3. 子表汇总结果；
4. 总表手工填写结果；
5. 取数来源及有效子表版本；
6. 汇总时间及汇总状态；
7. 完整性检查结果；
8. 总表审批状态及审批意见；
9. 子表调整对总表科目的影响；
10. 最终生效的预算结果。
11. 总表审批快照所对应的子表有效版本、模板版本和取数规则版本。

### 4.4 数据流转业务规则

```text
任务采用有效模板
  ↓
填报人形成子表草稿
  ↓
子表提交形成固定审批版本
  ↓
审批通过版本成为有效取数来源
  ↓
按科目汇总至原预算结果总表
  ↓
总表补充手工填写内容并提交审批
  ├─ 审批通过 → 正式预算结果
  └─ 总表审批状态为“审批拒绝”或“审批退回” → 子表调整或总表手工修改 → 重新汇总并提交
```

核心规则：

1. 草稿数据不得作为正式总表取数来源。
2. 审批中的子表版本不得替代当前有效版本。
3. 调整审批通过后，新版本才能替代旧版本。
4. 总表结果必须能够追溯到具体子表及其有效版本。
5. 子表调整只更新有关联的总表科目，不影响无关手工填写内容。
6. 总表审批通过后，当前总表结果成为正式预算结果。
7. 审批通过后的变更由现有“预算调整”管理。
8. 历史审批版本、驳回版本和调整版本应保留供查询。

## 5. 非功能需求

| 类别 | 业务要求 | 衡量方式 |
|---|---|---|
| 性能 | 任务列表、子表和总表应在可接受时间内展示；保存、汇总和提交后应及时反馈 | 以同时在线用户 1000+、同时编制任务数 1000+、单张子表 Sheet 数 50+ 为容量下限；列表、打开、暂存、汇总、附件生成和提交的响应时限，以及单 Sheet 最大行列/公式规模，须在开发启动前冻结为性能验收指标 |
| 并发 | 不同部门和不同子表应支持同时填报与审批，互不影响 | 支持 1000+ 同时在线用户；多人对同一子表暂存时以版本冲突机制防止覆盖 |
| 编辑冲突 | 多人可同时填写同一子表，但只允许基于当前草稿版本暂存 | 后暂存的旧版本不得覆盖先成功暂存的新版本，用户须重新加载 |
| 容错 | 保存、提交、审批或汇总失败时，不得错误显示成功，不得静默丢失已填写内容 | 异常后用户可识别失败原因并继续处理 |
| 数据一致性 | 总表应与当前有效子表版本一致；审批附件应与提交内容一致 | 任一总表科目均可追溯到对应版本 |
| 状态一致性 | 预算系统展示的审批状态应与实际审批结果一致 | 不出现已通过但仍显示审批中的长期状态 |
| 兼容性 | 沿用现有系统支持的办公环境和使用终端 | 以原预算编制结果录入模块当前正式支持的浏览器、分辨率和终端范围为准 |
| 操作时效 | 子表审批通过或调整通过后，总表应及时更新或明确提示待更新 | 在同一次操作完成后生成新的可核对汇总版本；具体响应时限纳入性能验收指标 |
| 可用性 | 人工填写区、计算区、只读区、异常区应容易区分 | 用户无需查看外部说明即可识别区域用途 |
| 可追溯性 | 关键任务、模板、填报、审批、调整和汇总行为应可查询 | 能按任务和版本还原业务过程 |
| 可理解性 | 业务错误提示应说明对象、原因和建议处理动作 | 禁止仅提示“操作失败”等无业务含义内容 |
| 数据保护 | 用户只能查看和处理授权范围内的预算数据 | 越权访问时不展示业务数据并给出权限提示 |

## 6. 外部/内部模块交互业务说明

### 6.1 与原预算编制结果录入模块的交互

| 阶段 | 过程管理业务行为 | 原结果录入模块业务行为 |
|---|---|---|
| 任务创建 | 建立总表与子表的编制关系 | 提供原总表内容作为任务最终载体 |
| 子表填报 | 各条线独立形成预算测算数据 | 暂不形成正式结果 |
| 子表审批通过 | 确定可用于汇总的有效版本 | 接收符合规则的科目汇总结果 |
| 总表编制 | 自动汇总子表数据 | 保留原手工科目的填写和计算逻辑 |
| 总表审批 | 校验子表来源和过程完整性 | 承载最终总表审批内容 |
| 总表审批通过 | 编制过程结束 | 总表成为正式预算结果 |
| 审批后调整 | 不再允许通过子表调整入口修改 | 进入现有“预算调整”流程 |

业务边界：

1. 新过程管理不是另建一份独立总表。
2. 新流程的总表就是原“预算编制结果录入”模块中的总表内容。
3. 原总表中不依赖子表的手工科目继续沿用老逻辑。
4. 新增过程只负责正式结果形成前的任务、子表、审批、汇总和调整。
5. 总表审批通过后不得同时存在“子表调整”和“预算调整”两个入口。
6. 任务下发后，任务关联总表的子表来源科目仅可由过程管理汇总更新；直接编制入口不得修改这些科目。
7. 总表审批使用封存的总表审批快照；后续子表有效版本变化只能更新可编辑总表版本，不得修改已提交审批版本。

### 6.2 与 SpreadJS 表格组件的业务交互

SpreadJS仅作为预算表格业务内容的操作载体，本PRD不规定其技术实现。

业务表现要求：

1. 按模板展示总表和子表的Sheet结构。
2. 清晰区分人工填写、自动计算、只读和异常区域。
3. 用户修改可填写内容后，相关计算结果应同步变化。
4. 支持按业务模板增加或删除动态明细行。
5. 动态行发生变化后，相关小计和总计应覆盖新增有效明细。
6. 审批中和审批通过的提交版本以只读方式展示。
7. 审批人看到的表格内容应与提交时的Excel附件一致。
8. 总表中来源于子表的科目应只读，并可查看来源说明。
9. 发生校验错误时，应定位到对应Sheet和业务位置。
10. 多人访问同一子表时，暂存操作须校验草稿版本，防止旧版本覆盖新版本。

### 6.3 与现有审批流程的业务交互

1. 子表与总表分别发起审批。
2. 每张子表拥有独立审批过程。
3. 子表提交审批时，形成包含全部Sheet的Excel附件。
4. 审批通过、驳回或撤回结果应反映到对应预算对象。
5. 子表审批通过后，才可成为总表有效取数来源。
6. 总表审批通过后，预算编制任务完成。
7. 审批节点、审批人和审批顺序继续由现有审批规则管理。
8. 审批流程不可用时，用户应看到明确提示，当前预算数据仍保持原状态。

### 6.4 与现有组织、账号和权限体系的业务交互

1. 用户身份、所属组织和基础权限沿用现有系统。
2. 预算任务进一步限定用户能够查看和处理的具体总表或子表。
3. 用户组织或岗位发生变化时，预算管理员可按任务交接规则调整未完成的编制责任和本地待办，已提交审批快照不受影响；BPM 审批待办不因该操作自动转交。
4. 无权限用户不得查看预算明细。
5. 权限不足提示：“您暂无该预算任务的查看或操作权限，请联系预算管理员。”

## 7. 异常场景与业务表现

| 异常场景 | 业务现象 | 用户可见提示 | 后续处理 |
|---|---|---|---|
| 子表校验不通过 | 无法提交审批，问题位置被标识 | “当前子表存在未完成或不符合规则的内容，请处理后再提交。” | 返回对应位置修改 |
| 普通依赖数据缺失 | 相关计算可能为零或不完整 | “该子表依赖的数据尚未完成，请核对计算结果后再提交。” | 不强制控制顺序，按业务判断处理 |
| 关键依赖数据缺失 | 关键依赖未形成可用数据 | “关键依赖子表‘{名称}’尚未满足提交条件，当前不能提交。” | 先完成或取得关键依赖的有效数据 |
| 关键依赖版本已过期 | 上游关键依赖调整审批通过，当前子表引用旧版本 | “关键依赖已过期，不能用于总表汇总。请发起调整重审。” | 从异常入口创建调整稿，默认带出上一有效版本并按最新依赖重算；审批通过后恢复总表取数资格 |
| 子表审批拒绝 | 子表业务状态恢复为“草稿”，本轮审批状态为“审批拒绝” | 展示拒绝人、时间和原因 | 填报人修改后重新提交 |
| 子表审批中被编辑 | 提交版本只读 | “该子表正在审批，当前提交版本不可修改。” | 等待结果或按权限撤回 |
| 子表审批通过后直接修改 | 原有效版本只读 | “该子表已审批通过，如需修改请发起调整申请。” | 进入调整管理 |
| 调整审批拒绝 | 新调整不生效，本轮审批状态为“审批拒绝” | “调整申请未通过，当前总表仍使用原审批通过版本。” | 修改调整稿后重新提交 |
| 重复发起调整 | 当前已有调整流程 | “该子表已有进行中的调整申请，请完成后再发起。” | 查看现有调整 |
| 总表已通过后发起子表调整 | 新增调整入口不可用 | “总表已审批通过，请通过现有‘预算调整’办理变更。” | 跳转或引导至预算调整 |
| 总表审批拒绝 | 总表业务状态恢复为“总表待提交”，本轮审批状态为“审批拒绝” | 展示拒绝原因；涉及的子表或科目由发起人自行判断处理 | 修改总表手工项或发起子表调整 |
| 总表存在未审批必填子表 | 无法满足完整性要求 | “必填子表‘{名称}’尚未审批通过，暂不能完成总表提交。” | 进入对应子表查看 |
| 取数来源不可用 | 相关科目无法形成有效结果 | “科目‘{名称}’的预算来源当前不可用，请联系预算管理员处理。” | 阻止提交总表 |
| 汇总结果发生变化 | 总表出现待核对标识 | “子表有效版本已更新，请重新核对总表结果。” | 总表主责人重新确认 |
| 总表审批状态为审批中需调整子表 | 审批版本已封存，不允许直接调整 | “总表正在审批，如需调整子表请先撤回总表审批或等待审批结果。” | 撤回总表审批或等待审批结果 |
| 版本冲突 | 用户尝试基于旧版本保存 | “该子表已产生新版本，请刷新后重新处理。” | 刷新并基于最新版本操作 |
| 保存失败 | 不显示成功状态 | “本次保存未成功，当前内容尚未提交，请重试。” | 保留当前内容并重试 |
| 提交重复操作 | 用户连续提交同一版本 | “该版本已提交，请勿重复操作。” | 展示当前审批状态 |
| 审批状态暂未更新 | 预算页面仍显示原状态 | “审批结果正在确认，请稍后刷新。” | 未确认前不改变有效版本 |
| Excel附件生成失败 | 无法完成子表审批提交 | “审批附件未生成成功，本次尚未提交，请重试。” | 重新提交 |
| 动态行未纳入汇总 | 完整性检查发现明细和汇总不符 | “新增明细尚未正确计入汇总，请核对后再提交。” | 阻止提交并定位问题 |
| 无权限访问 | 页面不展示预算数据 | “您暂无该预算任务的查看或操作权限。” | 返回授权范围页面 |
| 任务逾期 | 任务和待办显示逾期 | “该预算任务已超过计划完成时间。” | 继续处理并由管理员跟踪 |
| 总表审批退回 | 提交版本退出审批，审批状态变为“审批退回” | “总表审批已退回，请根据退回原因修改后重新提交。” | 恢复至总表待提交并重新完成完整性检查 |
| 子表审批退回 | 子表退出审批，审批状态变为“审批退回” | “子表审批已退回，当前版本可修改后重新提交。” | 发起人按现有审批流程权限在结果产生前撤回；调整退回时原有效版本继续有效 |

## 8. 已确认业务规则与遗留确认项

以下业务结论已回填至正文，保留本表用于追溯确认来源：

| 编号   | 待确认事项                             | 影响范围       | 回复                                                                                  |
| ---- | --------------------------------- | ---------- | ----------------------------------------------------------------------------------- |
| Q-01 | 同一编制主体、同一年度是否允许同时存在多个有效预算编制任务     | 任务唯一性      | 不允许；以“预算年度＋编制主体＋组织范围”校验，已作废任务除外。                                                    |
| Q-02 | 预算任务适用的组织层级，是集团、公司、项目还是允许多层级同时存在  | 任务范围和权限    | 允许多层级同时存在，独立不用汇总                                                                    |
| Q-03 | 预算期间仅按年度管理，还是还需管理月度、季度数据          | 模板和总表展示    | 需按照月度                                                                               |
| Q-04 | 哪些子表必须全部审批通过后才能提交总表，是否允许部分非必需子表为空 | 总表完整性检查    | 由预算管理员在任务下发前，按项目配置“必填子表”和“关键依赖”；关键依赖缺失时阻止子表提交。                                      |
| Q-05 | 子表依赖数据缺失时，是仅提醒仍可提交，还是部分关键依赖必须阻止提交 | 子表提交规则     | 部分关键依赖必须阻止提交                                                                        |
| Q-06 | 子表和总表审批中是否允许发起人主动撤回，以及可撤回节点       | 审批异常处理     | 允许；发起人按现有审批流程权限，在审批结果产生前撤回；撤回成功后该轮审批状态统一记为“审批退回”。                                                         |
| Q-07 | 总表处于审批中时是否允许直接发起子表调整              | 调整入口和版本一致性 | 不允许                                                                                 |
| Q-08 | 总表审批被驳回时，是否必须指定驳回涉及的子表或总表科目       | 调整定位效率     | 仅驳回总表审批状态，涉及的子表或科目由发起人自行线下联系相关人处理                                                   |
| Q-09 | 子表调整原因是否必填，是否需要上传业务说明材料           | 调整申请内容     | 需要有原因说明、附件材料上传                                                                      |
| Q-10 | 同一子表是否可以配置多名填报人；若可以，谁拥有最终提交权限     | 子表协作       | 可以多人；所有被授权填报人可提交当前版本，以先成功暂存的版本为准，后暂存者收到版本冲突提示并重新加载。                                 |
| Q-11 | 异常退出后的编辑锁定释放时长及管理员解除权限            | 编辑锁定       | 使用暂存和版本冲突控制，不设置编辑锁；未暂存内容默认不保存。                                                      |
| Q-12 | 任务下发后能否新增、删除或更换子表，以及已产生数据时如何处理    | 任务变更       | 不能；                                                                                 |
| Q-13 | 模板或取数规则变更后，是否允许应用到已下发但尚未提交的任务     | 版本管理       | 不能；既有预算模板或过程模板的后续编辑也不得替换任务已冻结的模板文件、科目或规则快照。                 |
| Q-14 | 人员离岗或组织调整时，未完成任务的交接责任与审批方式        | 任务连续性      | 不需要审批；预算管理员调整任务责任人（可多名）完成编制业务交接，不自动转交 BPM 审批待办。                                     |
| Q-15 | 任务、填报、审批及调整是否设置逾期升级规则          | 操作时效       | 本期不设置逾期升级；仅在任务列表和任务详情展示任务状态、截止时间及逾期标识。                                                                            |
| Q-17 | 预计同时在线用户数、同时编制任务数及单张表最大数据规模       | 并发与性能验收    | 容量下限：同时在线用户数 1000+、同时编制任务数 1000+、最大 Sheet 数 50+；响应时限及单 Sheet 最大行列/公式规模须在开发启动前确认并冻结。 |
| Q-18 | 任务作废、关闭及误下发后的处理规则                 | 任务生命周期     | 只能经 BPM 作废审批；通过后原任务保持只读，并自动为预算管理员生成一条待下发补偿新任务，不能撤销原作废。                              |
| Q-19 | 关键依赖上游版本变化后，下游如何完成重审并恢复总表取数资格     | 依赖闭环       | 下游标记 `DEPENDENCY_STALE`，任务列表异常筛选和任务详情展示处理入口；必须以旧有效版本为基础、按最新依赖重算后发起调整审批，审批通过并再次校验依赖后恢复可用。       |
| Q-20 | 子表之间是否允许跨业务条线或专业公司引用数据 | 数据隔离 | 不允许；依赖、公式取数和数据覆盖仅限同一业务条线/专业公司及任务范围内的子表。 |
| Q-21 | 总部至事业部/项目的额度下发及不超额控制是否属于本期 | 额度管理 | 属于本期；按模板与规则管理配置，支持逐级分配、提交占用、撤回/驳回释放及超额拦截。 |
| Q-22 | 重算如何触发，哪些状态可执行 | 汇总时效 | 支持事件自动重算、总表主责人手动重算及每日 02:00 定时重算；仅在任务业务状态为编制中或总表待提交时执行；总表审批状态为审批中时，其快照不重算、不改写。 |

## 9. 业务验收标准

以下为业务视角的验收判断依据，不作为逐步骤测试用例。

| 编号    | 验收事项     | 可验收判断依据                                                                                        |
| ----- | -------- | ---------------------------------------------------------------------------------------------- |
| AC-01 | 新旧模块边界   | 新过程的总表与原结果录入总表为同一业务内容，不产生两份相互独立的最终结果                                                           |
| AC-02 | 任务创建与下发  | 预算管理员能够创建包含总表、子表、责任人和时间要求的任务，并将待办发送给相关人员                                                       |
| AC-03 | 子表独立性    | 不同业务条线子表可并行填写和独立审批，任一子表驳回不改变其他子表状态                                                             |
| AC-04 | 多Sheet支持 | 一张子表的多个Sheet可作为一个完整业务对象填写、提交、审批和查看                                                             |
| AC-05 | 填写区域控制   | 填报人只能修改允许填写的内容，计算和只读内容不能被直接覆盖                                                                  |
| AC-06 | 动态行      | 用户新增或删除允许变化的明细行后，相关明细能够正确参与本表计算和汇总                                                             |
| AC-07 | 子表校验     | 存在必填缺失或业务规则错误时，系统能指出问题位置并阻止不合格内容提交                                                             |
| AC-08 | 子表审批版本   | 审批人看到的子表及Excel附件与填报人提交时的内容一致                                                                   |
| AC-09 | 有效取数来源   | 只有审批通过的子表版本能够成为总表正式取数来源                                                                        |
| AC-10 | 审批拒绝/退回     | 子表审批状态变为审批拒绝或审批退回后能够修改并重新提交，且保留对应记录                                                                       |
| AC-11 | 总表汇总     | 总表按当前有效子表版本和既定科目规则形成汇总结果                                                                       |
| AC-12 | 多模板差异    | 同一预算科目在不同总表模板中可以采用不同取数口径，且互不影响                                                                 |
| AC-13 | 手工科目保留   | 原总表中不来源于子表的科目仍可按原有业务逻辑填写和计算                                                                    |
| AC-14 | 来源追溯     | 用户能够从总表科目查看其来源子表、有效版本和最近调整情况                                                                   |
| AC-15 | 总表完整性    | 存在未审批必填子表、不可用来源、未完成手工项或关键依赖缺失时，总表不能被错误提交                                                       |
| AC-16 | 审批人权限    | 总表审批人可以查看子表依据，但不能直接修改子表数据                                                                      |
| AC-17 | 审批前调整    | 已审批子表在总表审批通过前可按确认后的状态规则发起调整审批                                                                  |
| AC-18 | 调整版本     | 调整审批通过前继续使用原有效版本；通过后新版本成为有效来源                                                                  |
| AC-19 | 调整联动     | 子表调整审批通过后，总表相关科目更新，无关手工科目不受影响                                                                  |
| AC-20 | 调整驳回     | 调整申请被驳回时，原有效子表版本和总表结果保持有效                                                                      |
| AC-21 | 总表重新审批   | 总表驳回后，完成手工修改或子表调整即可重新汇总并发起审批                                                                   |
| AC-22 | 正式结果形成   | 总表审批通过后，原结果录入总表成为正式预算结果，任务状态变为已完成                                                              |
| AC-23 | 审批后边界    | 总表审批通过后无法通过本次新增子表调整入口修改，并明确引导至现有“预算调整”                                                         |
| AC-24 | 多人填报暂存   | 同一子表多人不可同时填写；保存时需要进行版本校验。                                                                      |
| AC-25 | 版本冲突     | 用户基于旧版本保存时不会覆盖新版本，并收到刷新和重新处理提示                                                                 |
| AC-26 | 异常反馈     | 保存、提交、附件生成、汇总或审批失败时，不错误显示成功，并向用户说明处理方式                                                         |
| AC-27 | 过程追溯     | 能按任务还原创建、下发、填报、审批、调整、汇总和总表审批过程                                                                 |
| AC-28 | 权限隔离     | 用户仅能查看和操作其授权范围内的预算任务、总表及子表                                                                     |
| AC-29 | 原有能力兼容   | 本次上线不改变总表原有科目口径、手工结果录入及审批后预算调整规则                                                               |
| AC-30 | 遗留确认项关闭  | 第8章中响应时限及单 Sheet 最大行列/公式规模在开发启动前已冻结为明确指标                                                       |
| AC-31 | 月度预算     | 任务、子表、总表和汇总规则均可记录预算年度内的月度数据，并按模板定义的口径形成年度结果                                                    |
| AC-32 | 总表审批快照   | 总表提交审批后，审批人可查看与提交时一致的总表、来源子表版本、模板和取数规则；后续变更不得修改该快照                                             |
| AC-33 | 任务作废与交接  | 作废仅能经 BPM 审批；通过后原任务全量只读且生成待下发补偿新任务，驳回/撤回不生成补偿任务；管理员可将编制责任调整给一名或多名人员，不自动转交 BPM 审批待办，也不改变已提交审批快照 |
| AC-35 | 关键依赖过期状态 | 上游调整审批通过后，下游子表标记 `DEPENDENCY_STALE`；任务列表异常筛选和任务详情展示“关键依赖已过期需要重审”事项、变化版本与处理入口，不产生站内或外部消息                                 |
| AC-36 | 关键依赖强制重审 | 依赖过期子表不能用于总表汇总；从入口创建的调整稿默认带出上一有效版本并按最新依赖重算，只有调整审批通过且依赖复核通过后才恢复总表取数资格                           |
| AC-37 | 模板快照隔离 | 任务下发后编辑既有预算模板或过程模板，不改变该任务的表格结构、科目、填写控制、计算、依赖、取数结果、草稿、提交版本或审批快照 |
| AC-38 | 过程模板发布 | 只有完成过程元数据并通过发布校验的版本可供新任务选择；已发布版本修改时必须复制为新版本，不能覆盖编辑 |
| AC-39 | 模板复制完整性 | 复制过程模板形成新版本时，SpreadJS 模板文件、区域元数据、科目、依赖、校验和规则关联均完整复制，且新版本可独立发布和停用 |
| AC-40 | 遗留模板兼容 | 未补齐过程元数据的既有模板仍可按原用途使用但不能下发过程任务；被任务或快照引用的版本停用后仍可只读查看和追溯 |
| AC-41 | 业务条线隔离 | 不同业务条线或专业公司的子表不能配置跨线依赖、公式取数或数据覆盖；违规配置在保存和发布时均被拦截 |
| AC-42 | 额度逐级分配 | 总部可向事业部、事业部可向项目分配年度/月度科目额度；任一层级累计分配额和下级提交占用额均不得超过上级可用额度，并可追溯占用、释放和生效记录 |
| AC-43 | 重算控制 | 支持总表主责人在允许业务状态手动重算；每日定时任务仅重算存在变化、失败或待核对的允许状态任务；总表审批状态为审批中时，其快照不被重算结果覆盖 |

## 关键PRD风险提示

1. **新旧模块职责重叠风险**：总表既是原结果录入载体，又是新过程汇总结果。任务绑定、来源科目只读和直接入口拦截规则必须与现有总表能力联调验证，避免重复录入或汇总覆盖。

2. **审批快照与版本一致性风险**：总表审批状态为审批中时禁止发起子表调整，且审批使用封存快照。需与现有审批流程联调验证撤回、重新汇总及来源版本追溯，确保审批内容与正式结果一致。

3. **模板、额度与依赖复杂度风险**：主营公司、专业公司以及不同业务条线存在差异化模板；跨业务条线依赖必须被拦截，同一业务条线内的跨子表依赖、额度分配与科目取数须在上线前完成业务核对，否则容易造成总表漏取、错取或额度超额。

PRD 落地版已完成。性能响应时限及单 Sheet 最大行列/公式规模须在开发启动前冻结。
